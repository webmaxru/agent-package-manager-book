Objective

After this chapter you can take agent context that already works in one repo — a prompt, an instruction set, a skill — and extract it into a standalone, versioned APM package that other teams install through the same Chapter 5 apm install loop, instead of copying the files by hand. You will see why copy-paste reuse quietly recreates Chapter 1's drift, author a producer apm.yml, snapshot the package with apm pack, and read the crucial producer/consumer symmetry: producing adds no fifth property — it makes you the source of Portability, Reproducibility, Provenance, and Governance for everyone downstream.

Edition 1.2 — inspected CLI: exactly APM 0.31.0. The current worked example uses a separate local-bundle fixture; it does not silently change the original Meridian manifest. Clearly labelled v0.23.1 snapshots preserve the earlier package and private-Git story, not a claim that their historical outputs were produced by this release.

Concept/Theory

Reuse-by-copy is the Chapter 1 problem wearing a helpful face

Chapter 1 opened on drift: three copies of a review prompt in three home directories, each checking a slightly different threat model. Chapters 4–9 fixed that inside one repo — a manifest, a lockfile, a policy gate. But the moment a second team wants your good prompt, the old failure is one paste away. Copy the checkout-review prompt into another repo and the two copies begin to diverge immediately: no shared version, no lockfile, no review trail, no way to answer “which prompt produced this behaviour?” The uncomfortable truth this chapter names is that reuse-by-copy recreates the exact drift the book set out to kill.

Producing is the fix. It is the act of extracting context that already works — a prompt, a skill, an instruction set — into a standalone, versioned APM package that other repos install through the normal apm install loop, rather than copying files by hand. A copy is a point-in-time snapshot that starts drifting the instant it is made; a dependency is a pinned, hashed reference that a lockfile can reproduce and apm update can advance deliberately (Chapter 7). Producing converts copies into dependencies. APM frames the whole ramp around one promise: “there is no separate ‘build pipeline’ — the CLI is the build pipeline” (Producer overview).

Misconception: “we already reuse our prompts — we just copy the files”

Copying is the anti-pattern, not the solution — it is the Chapter 1 drift problem with a friendly face. Reuse only becomes governed reuse when it flows through a versioned package: one name, one version, one reviewable source that consumers restore for their supported targets instead of maintaining independent forks.

Meridian can keep apm.yml + .apm/

Here is the part that removes the intimidation: Meridian needs no separate packaging language. Its producer package is a directory with apm.yml, a .apm/ source tree, and a README for consumers. That remains a good authoring layout, but it is not the only installable shape: root skills, skill collections, and plugins have their own intake rules (APM 0.31.0 package types).

You already know this shape from both sides. In Chapter 3 and Chapter 4 you authored primitives under .apm/instructions/ and .apm/prompts/; in Chapter 5 you consumed other people's packages that had exactly those directories. Producing is not new authoring — it is relocation into a package shape. The same source-vs-build split from Chapter 3 is now your responsibility: .apm/ is what you author; APM-managed files under .github/, .claude/, .cursor/, and shared .agents/ are deployment output. The generated lockfile is still a reviewable record to commit when sharing a reproducible project (Chapter 6). “Edit the source under .apm/ and re-run apm install — never edit the deployed copy” (package anatomy).

The symmetry: everything you consumed, you now become the source of

Producing does not add a fifth property to the book's four. It flips your role. Every benefit the earlier chapters named as a consumer win, the reader now supplies to downstream teams. When Meridian ships meridian-standards, its consumers get:

  • Portability — one manifest compiles the same supported intent onto Copilot, Claude Code, and Cursor, not necessarily identical native bytes (Chapter 5);
  • Reproducibility — declared Git dependencies get a resolved_commit and content_hash, so unchanged intent and its lock can be replayed; a packed bundle also records a per-payload-file SHA-256 map (Chapter 6);
  • Provenance — a pinned, hashed, reviewable source that passes the same install-time scanners from Chapter 8;
  • Governance — the package installs through the same apm-policy.yml gate from Chapter 9; a policy can even require it, as Meridian plans to do with require: meridian-finance/meridian-standards once the package is available.

This is the spine sentence of the whole book landing: the reader stops being an npm user and becomes an npm publisher — the same manifest, lockfile, and policy discipline, now pointed outward. APM states the symmetry directly: “every package you publish here installs through the [consumer ramp's] apm install command” (Producer overview). The official ramp is a five-rung ladder — author → compile → preview → pack → publish — and this chapter walks the two rungs that matter for internal reuse: author the package, and pack it, then closes the loop by installing the result back into a scratch repo. “You don't need a marketplace to start” (Producer overview).

Choose a contract that preserves what you are sharing

A package name, a distribution format, and a harness are different things. Putting a prompt in a ZIP does not make it a skill; adding a schema URL does not make every harness able to load it. Portability is bounded by the components the format carries and the consumer supports. The format choice below implements that boundary. Meridian must keep its engineering instructions, checkout-review prompt, and review skill together; a skill-only format is not an upgrade for that package.

Meridian

A second Meridian service asks for the checkout-review prompt and the fraud-domain engineering rules. The Chapter 1 move would be to paste them into a Slack thread — and start the drift clock. Instead, the platform team makes the pivot from consumer to producer: they lift the checkout-review prompt, the shared engineering instructions, and the secure-payment-review skill out of meridian-checkout and into a new package, meridian-standards, owned by Meridian Platform Engineering. Every one of those files already existed in the checkout repo — producing is relocation, not new work. By the end of the chapter that package will come back in to meridian-checkout as a pinned dependency, and the version graduates to 1.0.0.

In APM

For current commands, $Apm means the absolute path to the checksum-checked 0.31.0 executable from Chapter 5's setup, not whichever apm is on PATH. Use short, disposable copies outside the book checkout, with isolated user/config/cache directories. Fixture names below are relative to backend/examples/updates/1.2/producer/; copy the whole fixture, including hidden source directories and its genuine lockfile. No example needs a live agent session.

A producer package is a directory you already know how to read

Here is meridian-standards as a plain directory. Nothing is scaffolded by a special tool: an apm.yml, a README.md, and one subdirectory per primitive type under .apm/. Read it and you will recognise every file from earlier chapters.

Keep Meridian's primitives under .apm/<type>/; do not mix in extra root directories expecting APM to union every possible layout. Source authority determines which files count. In this APM layout, commands are authored as prompts: .apm/prompts/*.prompt.md, not a new .apm/commands/ directory (author primitives).

The producer manifest: identity + distribution intent

A consumer manifest answers “what does my repo need?” A producer manifest also answers “who is this package, where does it come from, and what is it for?” so other people can evaluate and discover it. It is the same apm.yml schema you wrote in Chapter 4 — producers simply fill in the optional distribution fields a private consumer manifest can leave out. Keep the original Meridian manifest visible: its omitted dependency mapping explains its output mode.

In 0.31.0, name and version remain the required identity fields. description, author, license, repository, and keywords are optional distribution metadata. A string author becomes a { "name": … } object in generated plugin metadata; repository and keywords also survive synthesis. These fields help consumers review ownership and reuse terms; a repository URL is not publisher authentication, and the producer's MIT license does not license every dependency. targets names the supported destinations; it is not decorative metadata (0.31.0 manifest reference).

HYBRID layout is not the type: hybrid switch

A root SKILL.md alongside apm.yml is a supported HYBRID layout, with separate human-facing and runtime descriptions. That does not activate the manifest's type key. The 0.31.0 reference still reserves that field; changing Meridian's value to prompts in a control did not suppress its instruction or skill. Keep type: hybrid as metadata, not a content filter or permission to bypass a distribution format's restrictions (layouts; reserved field).

The metadata is not decorative: it becomes the package's identity card on the other end. When you do not author a plugin.json yourself, apm pack synthesises one from apm.yml — so apm.yml stays the single source of truth (pack a bundle):

Packing turns reviewed context into a handoff artifact. First ask which output your manifest requests, then inspect its contents. In 0.31.0 these output branches can coexist; a successful command is not, by itself, proof that an archive was created (pack routing).

Publication authority: local source versus attested dependencies

Chapter 4's declaration principle applies at publication, too: a directory's existence does not automatically authorize shipping it. For local plugin packing, .apm/ selects Meridian's source layout; an explicit includes list is exhaustive. This is not the same operation as install discovery (pack source selection).

Same declaration, different operation. apm 0.31.0
InputObserved boundary
.apm/ plus root skills/, with includes: auto Local pack selected .apm/; the extra root skill was omitted with a warning.
includes: [skills/unlisted] Pack shipped only that explicitly listed root skill, not the unlisted .apm primitives. A missing listed path failed before writes.
An includes list naming only one instruction, followed by apm install The unlisted instruction still installed. Includes is advisory for install, not a discovery allowlist.

Intake also respects declarations: an eligible APM manifest, backed by .apm/ or APM/MCP dependencies, takes precedence over a co-located plugin marker. Metadata-only apm.yml does not automatically override a plugin; root skills and collections remain distinct supported layouts. For a plugin, "skills": ["./skills/review"] declares the complete skill set, "skills": [] means none, and omission permits conventional discovery. Extra undeclared directories cannot expand an explicit list (package and component authority).

Your own source and someone else's dependency have different authority. A local prompt edited after install was packed with its new source content, not the older deployed copy. Dependency input, by contrast, is limited to the lock's deployed_files. For files selected for export, a missing file or a mismatch against recorded deployed_file_hashes fails packing; extra or edited cache content cannot become the publishing source. Older locks may lack recorded hashes; compatibility with those locks is not retroactive attestation of every file (dependency attestation). Install and audit before packing as a validation habit, not because every local file is read from the last deployment.

Scaffold deliberately; do not confuse the two plugin families

The distribution contract is a choice, not a filename heuristic. apm plugin init without a format flag still creates apm.yml plus a Claude-compatible root plugin.json. Strict Agent Plugins 1.0 is opt-in and also creates mcp.json, with pinned schema URLs. Both scaffolds start at version 0.1.0, include empty runtime/dev dependency sections, and create neither a skill nor a lockfile (plugin scaffolding).

Catalog generation and release checking are different operations

A marketplace is a curated discovery index, commonly hosted in Git, not the REST package server. Use it when teams need to find several approved packages; one shared package can simply use a Git ref. apm marketplace init scaffolds the index declaration; apm pack generates its catalog. Consumers register a reachable Git-hosted catalog through apm marketplace add (marketplace producer flow).

A release check answers a different question: does the reviewed catalog match what these declarations and available metadata would generate? The marketplace fixture makes that question network-independent by keeping its single plugin under plugins/review/. Its plugin manifest explicitly declares only skills/review.

--check-clean is read-only for project files, including modification times. A changed catalog returned 4 and was not repaired. A missing effective output path also returned 4; an override such as --marketplace-path claude=alternate/marketplace.json changes what is compared, not permission to create it. Use catalog/marketplace.json for the output path: the tested parser rejected a leading ./ there as traversal (release gates and effective paths).

Run in a disposable metadata-offline fixture with an initially empty isolated metadata cache. Its pinned public source has no obtained metadata: offline does not mean certifiable. apm 0.31.0

A clean catalog is not a verified bundle

In a project requesting both bundle and marketplace output, --check-clean suppressed normal writes even with --force --archive. Deleting that project's ZIP still left the clean catalog check at exit 0: it neither rebuilt nor certified the bundle. Use the actual archive-to-consumer test for that boundary, not a marketplace comparison.

The registry client exists; a public hosted hub is a separate claim

APM 0.31.0 ships an experimental REST registry client and an implementable HTTP API v1, including version-list, archive-download, and publication operations. That is not evidence of a Microsoft-operated public searchable hub, nor is a Git transport proxy the same service. Real use needs a compatible backend and authorized access. Git remains the default distribution route (experimental registries; HTTP API v1).

The registries feature is disabled by default; both gated manifest parsing and publish preview fail until it is enabled. This local-only preview demonstrates the separate registry archive contract, without uploading:

For engineering leaders

This is the step that converts tribal knowledge into a reusable, governed platform asset. The checkout team's review conventions were previously trapped in one repo and spread by copy-paste; packaged as meridian-standards, they become a named, versioned, reviewable dependency that any team installs with one command — and that your Chapter 9 policy can require. The payoff compounds the moment a second and third team consume the same approved conventions: a fix or a new rule ships once, as v1.1.0, and every consumer picks it up through the normal update loop instead of drifting. The question to put to your platform group: which of our best-practice prompts, instructions, and skills should be internal packages rather than wiki pages nobody re-reads?

When to use / pitfalls

How to hand a package off

Pick the channel by the consumer's needs, not by the word “publish.” For normal versioned internal reuse, a declared Git ref is the simplest default. A hand-carried artifact and a replayable dependency are different contracts.

Choosing a distribution channel for a produced package.
Channel What it is Reach for when…
git ref (owner/repo#<ref>) Declared source, pinned and hashed by the lockfile; no central APM service required. the consumer can reach your git host. Default choice for internal reuse.
bundle (apm pack --archive) A payload and embedded hash inventory; dependencies: {} permits local-only production. you need an artifact handoff. Retain it for reinstall; the imperative ZIP route is one-shot deployment.
marketplace A curated discovery index (apm marketplace add), not a REST archive service. many repos need to discover many curated packages.
registry (apm publish) Experimental consumption/publication against a compatible REST service. your org has reviewed that backend and its access controls; a Git proxy alone is not one.

Pitfall: inspecting an exit code instead of the intended inventory

Install and audit the producer, preview the pack, then inspect the real output. Confirm both routing and source selection: the old manifest's successful archive command creates no ZIP, while the new empty-mapping fixture does. A file excluded by a declaration cannot be recovered by checking the final hash inventory — you must first know which primitives should have shipped.

Pitfall: treating legacy tooling as the same bundle path

The tested legacy --format apm Copilot pack silently omitted the public style-checker skill deployed under shared .agents/skills/, producing an empty archive with exit 0. This is a real 0.31.0 bug, not a network skip. A nonempty instruction packed and restored successfully, and default Claude-compatible packing retained the skill. Do not generalize either result to all formats or all primitives (legacy pack implementation). Pack's --target and apm unpack remain deprecated tooling surfaces; Chapter 11 treats workflow compatibility separately.

Integrity is not a signature, and reproducibility is not a clock

The embedded lock's pack.bundle_files maps payload-relative paths to SHA-256 digests; the lock cannot hash itself. Changed, missing, and extra payload files in genuine bundle controls were rejected before project writes. That protects integrity relative to trusted metadata, not publisher identity: someone who replaces both payload and hash manifest is not authenticated by either. A clean scan or an unsigned SBOM is not a safety certificate (Chapter 8).

New locks omit generated_at, but repeated ZIP packing can still change pack.packed_at and archive member timestamps while leaving payload bytes unchanged. Do not promise identical ZIP bytes merely because dependency locks match (Chapter 6; bundle integrity contract).

Worked example

The producer → consumer round-trip

The real test of a produced package is not that it packs — it is that it stands alone. Local primitives can lean on paths, tools, or context that only exist in the origin repo, so the producer's discipline is to install the package into a fresh, throwaway repo and check that the intended context deploys there. “Install your own package in a scratch repo before declaring it shipped” (Producer overview). This is the consumer ramp from Chapter 5, seen from the producer's chair.

The v0.23.1 example tested a local-path source install, not an archive. The current source control also succeeded with apm install ./pkg and retained the relative ./pkg dependency spelling: local adds do not invariably become absolute paths. A local source still has to travel with its consumer; it is not an immutable Git pin. The separate test below instead consumes a real generated ZIP.

1. Pack the separate local-only Meridian fixture

Copy local-bundle/ to a short disposable directory. It reuses all three Meridian source files, trims optional discovery metadata, and deliberately declares an empty dependency mapping. The original backend/examples/ch10/meridian-standards/ is unchanged.

The actual directory is build/meridian-standards-1.0.0/, and the actual ZIP is dist/meridian-standards-1.0.0.zip. Alongside generated plugin.json and the enriched embedded lock, both contain:

  • instructions/meridian-engineering.instructions.md — the engineering rules;
  • commands/checkout-review.md — the authored prompt in the bundle's command layout;
  • skills/secure-payment-review/SKILL.md — the review skill.

Packing enriched the embedded copy of the lock with bundle metadata without changing the producer's root lock. The output is a Claude-compatible plugin bundle, not strict Agent Plugins 1.0 and not the flat registry archive.

2. Install that ZIP into a fresh three-target consumer

In another empty scratch directory, replace the placeholder with the absolute path to the ZIP you just created. Pass the targets on the install command as well as init: without that explicit install flag, the 0.31.0 ZIP probe deployed only to Copilot despite a three-target consumer manifest.

The imperative route did not add the archive to dependencies.apm. Its real lock recorded local_deployed_files, hashes, and local-bundle ownership, not a replayable archive dependency row. Retain the artifact for reinstall; do not assume a later bare install can recover it from the manifest. 3. Use declared Git for the ordinary restore contract

For day-to-day sharing, return to Chapter 5's declared-source loop. The small pinned-bundle fixture selects one public skill at an immutable commit, avoiding the full sample package's floating transitive graph. Explicit git keeps it Git-sourced even if registry defaults are configured. Unlike the one-shot ZIP, this declaration tells the next clone where to obtain the dependency again.

The genuine lock records the full commit and the virtual skill's version: unknown; do not invent a semantic version for that subpath. Its deployed skill bytes are the attested dependency input to pack. Frozen replay here checks unchanged declared Git state, not deployed-content integrity; that is why audit is separate (Chapter 6).

Inspect build/pinned-bundle-1.0.0.zip on disk. This release's successful JSON report left bundle: null even while creating that archive; the JSON envelope is not a complete artifact inventory and null is not proof of absence (0.31.0 pack reporting).

Meridian's payoff: the extracted conventions come back as a dependency

In the story, Meridian publishes the source to its private Git host, tags v1.0.0, and makes meridian-checkout depend on it. The historical manifest below preserves that graduation to 1.0.0. Private distribution remains SKIPPED-needs-network: no real authorized Meridian repository or publication was supplied. The public declared-Git example above proves the current mechanism, not the fictional host.

Carry the earlier consumer decisions forward: merge this dependency into the existing reviewed declarations, including Chapter 8's local-fetch MCP declaration, the other packages, and the review script. The reduced snapshot's mcp: [] and omitted script do not direct you to erase them. Retiring any existing dependency or capability requires its own reviewed change.

That dependency is the payoff of the whole book. The checkout team no longer copies its own conventions between services — it depends on them. Once the private source is available, the normal Git loop records its commit and content hash (Chapter 6), scans deployable content (Chapter 8), and gives Chapter 9's policy a named package to require. The same approved version can then supply each service's supported native context. The four properties the reader consumed for nine chapters are now the four properties they produce.

Recap & next

Recap

  • Reuse-by-copy recreates Chapter 1's drift. Producing turns a working convention into one versioned, reviewable package that consumers restore identically — a dependency, not a fork.
  • Meridian keeps its familiar source layout: apm.yml plus .apm/, not the only supported package shape. Producing is relocation, not new authoring; type: hybrid remains reserved metadata, not a layout or format switch.
  • Pack routes by declaration. The unchanged historical manifest still writes in-tree plugin manifests. The separate dependencies: {} fixture produces a real default Claude-compatible directory and ZIP containing all three Meridian primitives.
  • Publication authority is explicit. Local packing follows selected source and exhaustive includes; install does not use includes as a discovery allowlist. Dependencies supply attested deployed content, not arbitrary cached files. Dev tooling stays out of the bundle.
  • Formats and support are bounded. Strict Agent Plugins 1.0 carries skills/MCP, not Meridian's complete package. Native registration works, but its known canonical-IR audit failure is separate from runtime loading. Bundle hashes detect changed payload relative to trusted metadata; they are not signatures.
  • Catalog checks are read-only, not bundle certification. Drift or uncertifiable clean checks return 4; incomplete strict metadata returns 5, including when both gates are combined. A marketplace index, a Git proxy, and the shipped experimental REST registry client/API are different things; none proves a public hosted hub.
  • Meridian extracted its checkout-review prompt, engineering instructions, and secure-payment skill into meridian-standards. The current example proves offline ZIP deployment with explicit copilot,claude,cursor targets; it is one-shot, unlike declared Git restore. The story closes with the conventions returning as a private dependency and meridian-checkout graduating to 1.0.0, without claiming a live publication.
