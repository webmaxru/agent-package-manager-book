Objective

After this chapter you can read the source identities, hashes, and deployment ownership in apm.lock.yaml, compare a restored setup with its recorded state, distinguish apm install --frozen's limited structural checks from content audit, and use apm lock and apm find to separate resolution from deployment and trace a tracked file's origin.

Edition 1.2 — inspected CLI: APM 0.31.0. Chapter 5 made the lockfile appear as a by-product; here it becomes the subject — Reproducibility made mechanical. Current examples use small recorded fixtures; the explicitly historical v0.23.1 snapshot keeps its original evidence boundary.

Concept/Theory

A manifest resolves; a lockfile freezes

The package installs in Chapter 5 wrote apm.lock.yaml. You noticed resolved_commit and content_hash in the Git example without yet studying them. Now ask the lockfile question familiar from npm, pip, or Cargo: how does another checkout reproduce a reviewed result rather than resolve whatever is newest?

The answer is a distinction. A manifest declares intent, and intent is often a moving target: a dependency's ref can be a branch (main), a tag (v1.2.0), a commit SHA, or a semver range (^1.2.0). A branch can move; a range can admit a newer matching tag. Two fresh resolutions without the same lock can therefore select different content from the same manifest. That is the agent-context version of “works on my machine.”

The lockfile records the resolution and deployment ownership. For unchanged Git declarations, install reuses the recorded graph, including transitive commits and manifests. Upstream changes do not silently become new inputs to that replay. Ordinary install can instead reconcile edited declarations or local sources; a missing lock permits fresh resolution. Keep the manifest, lock, local sources, targets, and CLI version together when comparing results (0.31.0 lockfile and replay contract).

Three questions, source-specific answers

Separate what you requested, what was selected, and how content is checked. For Git, resolved_ref → resolved_commit → content_hash illustrates those questions. It is not a universal field set:

A source coordinate answers where; a hash answers which content. Neither authenticates a publisher or proves a prompt benign. name and ordinary Git/local version are self-asserted inventory metadata. The pinned skill's version: unknown does not weaken its immutable Git commit; registry and Git-semver versions have separate resolution roles (identity and metadata fields).

The hash follows the bytes, not the ref

The historical v0.23.1 Meridian captures make this distinction concrete: separate resolutions selected transitive commits a4aebcd4… and 3169734b…, yet the selected skill's tree hash stayed sha256:9236d06a…. These were not two replays of one unchanged lock. The manifest's transitive edge floated; each generated lock still pinned its selected commit. The risk is the next fresh resolution, not an upstream branch overriding an existing pin.

  • Package-tree content_hash: sorted relative paths and actual materialized file bytes. GitCache-backed subpath checkouts set core.autocrlf=false, but that does not override every .gitattributes or core.eol rule, or rewrite CRLF committed in source.
  • Deployed-file hashes: UTF-8 text normalizes CRLF to LF; binary content is hashed raw. Changing only line endings can therefore change disk bytes without changing the canonical deployed-text hash. Copilot, Claude, and Cursor projections can legitimately have different frontmatter and different hashes.

The 0.31.0 instruction probe changed all six deployed files to CRLF: CI audit exited 0, with the lock unchanged. That proves the deployed-text normalization boundary, not universal cross-platform package-tree or cross-harness byte equality (hash definitions).

Generated, never hand-edited

apm.lock.yaml is a generated record, not an authored file. You edit apm.yml; APM writes the lockfile. The review story lives in the diff: regenerate after an intended change, then review which identities, hashes, and ownership rows moved. Generated does not mean authenticated — protect and review both files. Reproducibility is not staleness, either: refreshing an unchanged declaration deliberately is the apm update workflow in Chapter 7.

Meridian

Priya adds a new shared Git dependency to the checkout project — selected by a branch ref and absent from the old graph — and pushes the branch. On her laptop everything works: apm install resolved the package and updated apm.lock.yaml locally. But she commits only the apm.yml change and forgets to commit the regenerated lockfile. CI runs apm install --frozen, and the build fails: the manifest now names a Git package the committed lockfile does not pin, so this missing-dependency check catches the disagreement. The fix is not to hand-patch the lockfile — Priya runs apm install to reconcile, reviews the lockfile diff in the pull request (the new package's resolved_commit and content_hash appear), and commits it. The reviewed setup restores again, and the team adopts a rule: the lockfile is the reproducibility contract, reviewed and committed like the code it pins. Note what did not happen — no upstream ref “moved”; the break was a Git declaration that had outrun its own committed lockfile. This case does not make --frozen a veto on every declaration change; its local-path exception matters below. Whether to take a newer version at all is Chapter 7.

In APM

Inside apm.lock.yaml

Read the file as a resolved inventory plus an ownership record, not just a list of versions. The worked fixture contains one local package and one workspace instruction, each projected to Meridian's three targets. Its real lock makes the local-versus-Git distinction visible:

Each deployments row identifies a destination through kind, target, value, runtime, and scope. owners records its claimants, oldest to newest; active_owner names the current one and must be a member of that list. Here the dependency's ownership key is ./package, while . owns the workspace instruction. A row's content_hash describes that deployed content, not the dependency's entire tree. Native-entry and directory rows need not carry a file hash (canonical ownership rows).

The compatible per-dependency deployed_files list and deployed_file_hashes map remain in the full file. Root .apm/ outputs also retain local_deployed_files/local_deployed_file_hashes. A larger Git graph adds depth and resolved_by for transitive provenance. An MCP-only project can have an empty APM dependency list alongside mcp_servers, mcp_configs, mcp_target_servers, and URI ownership rows. Do not infer one dependency shape from another.

New locks omit generated_at. A legacy timestamp was retained on an unchanged restore, but it is not a change oracle. Git-semver locks still record constraint, resolved_tag, and resolved_at under format '2'; registry locks also use format '2'. Even apm_version is optional: Chapter 5's root-local-only lock omitted it. Prove a no-op by comparing complete lock bytes and expected outputs, as in the current restore exercise, not by watching a timestamp or an installed-package counter.

apm install --frozen — a limited structural gate

CI should not silently invent an unreviewed dependency resolution. Frozen install requires an existing lock and checks structural conditions, including missing direct Git dependencies and declared MCP configuration. But it is not a universal declaration-change veto. The independent Chapter 5 check added a new local path declaration while retaining the old lock: frozen install exited 0, deployed the new skill, and rewrote that lock. The direct-dependency presence checker skips local paths (0.31.0 structural check).

Frozen install can materialize files and change lock metadata; its successful exit does not prove that the committed contract stayed unchanged. Nor is it an audit of native file bytes. The CLI's reminder is literal: Lockfile presence verified. Run 'apm audit' for on-disk content integrity. With unchanged Git declarations, a moving upstream branch is handled by replaying the locked commit, not by comparing the remote branch during preflight (frozen mode and locked replay).

Audit can replay in scratch — cold is not offline

apm audit --ci checks supported content, consistency, and ownership separately. It can acquire locked sources into an owned scratch replay when modules/cache are absent. Clean public and local cold probes left the checkout unchanged; public replay with acquisition deliberately unavailable exited 1, not a harmless skip. Cold public restore or CI audit may need network access. A warm cache or local-only success is not proof of an offline deployment plan (CI scratch replay).

Audit is not a universal native-configuration check either: in the tested MCP-only project, CI audit did not detect missing or edited native MCP configuration. Frozen install recreated the missing file but left the edit intact. Check such harness-specific state separately rather than treating a clean exit as byte certification. Chapter 7 develops audit; Chapter 8 develops its security boundaries.

apm lock — write the contract without deploying

Sometimes you want to resolve a declaration for review without altering harness files. apm lock separates those jobs: it can acquire/materialize dependency metadata and write the lock, but does not deploy or delete harness files. Crucially, it preserves existing deployment state for later reconciliation (lock-only behavior).

Keeping ownership is not proof that files are still present. After a target contraction, lock-only generation also retained Claude/Cursor files and their ownership; ordinary install performed the cleanup. Use apm lock to compute the record without deployment, not to repair a missing file or erase cleanup history.

An SBOM timestamp is a different clock

Inventory export serializes a lock; it does not re-resolve or authenticate its contents. The inspected help documents apm lock export --timestamp as an SBOM timestamp control, with fallback to SOURCE_DATE_EPOCH, a legacy lock timestamp, then the Unix epoch. That help/source contract is distinct from execution evidence: separate producer probes actually exported CycloneDX and SPDX and repeated the fixed-timestamp CycloneDX export byte-identically. Neither operation restores generated_at to new locks (inventory export).

apm find — trace a tracked file to its origin

“Where did this instruction come from?” is the provenance question behind apm find. It reads the lock's deployed-file records; --source adds the source coordinate. This is a lookup, not a fresh hash check or publisher authentication (provenance lookup).

For engineering leaders

Reproducibility is the bridge between developer experience and compliance, and the lockfile is its load-bearing beam. On the DX side, a reviewed manifest/lock pair, fixed CLI and targets, and available local sources replace hand-copying with repeatable materialization. On the compliance side, the lock is a reviewable inventory of source identity and deployment ownership; apm find traces recorded files, not everything a runtime might read. If you cannot identify which agent context shipped, investigating a regression becomes archaeology. Require frozen installation with an unchanged-contract comparison and separate integrity checks, not frozen's exit code alone. Review the lockfile diff like a code dependency change; do not mistake an unsigned inventory for publisher or runtime attestation.

When to use / pitfalls

Treat the lockfile as a contract

Choose the job first: replay, reconcile, verify, resolve without deployment, or trace provenance. A successful command answers its own question, not all five.

Which lockfile-related command to reach for, by intent.
You want to… Run… Because
set up or re-materialize a cloned repo apm install (bare) Replays unchanged Git intent; reconciles changed declarations or local sources (Chapter 5).
materialize a reviewed contract in CI apm install --frozen Requires a lock and performs limited structural checks; also reject unexpected manifest/lock changes.
check supported deployed content and ownership apm audit --ci Separate integrity/replay checks; cold acquisition can need network and native coverage varies.
resolve/review without changing harness files apm lock Writes resolution state, retains existing deployment ownership, deploys/deletes no harness files.
find where a deployed file came from apm find <file> Looks up recorded ownership/source, not current integrity or publisher identity.
move to newer versions apm update (Chapter 7) Reproducibility is not staleness; review intentional refreshes separately.

Pitfall: never hand-edit apm.lock.yaml

Hand-patching the lockfile to make CI green produces a lockfile that no resolution actually created — a fiction that will mislead the next restore and the next audit. When --frozen reports drift, the correct fix is to change the manifest if needed and regenerate (apm install, or apm lock for resolution review before deployment), then review and commit the resulting diff. Fix the recipe and rebuild the record; do not forge the record.

Pitfall: --frozen checks structure, not bytes

Do not turn “presence verified” into “all declarations and native bytes match.” New local declarations, equivalent Git refs, and promoted transitives can change a lock during frozen install. Managed instructions can be repaired rather than rejected. Use apm audit --ci for the separate supported integrity checks; ordinary bare audit treats routine replay drift as advisory. Neither command proves every native MCP file correct.

Commit the re-locked file — and review its diff

Treat the diff with the same seriousness as a package-lock.json change. The nearest safe materialization workflow is:

  1. Pin the CLI and manifest targets; include reviewed local source directories.
  2. Save the committed manifest/lock bytes, run apm install --frozen in a disposable checkout, and fail CI if either file changed — even when install exited 0.
  3. Run apm audit --ci, and check native configuration separately where coverage requires it. Investigate a failure; do not suppress drift to obtain a clean result.

If CI's purpose is to verify already committed deployments, audit before installing: a restore can repair the evidence you meant to inspect. Meridian commits its authored sources, manifest, lock, and reviewed harness outputs; apm_modules/ is auto-gitignored materialization, not the source of truth. Protecting the CI job and its policy inputs is Chapter 11's concern.

Recap & next

Recap

  • The manifest names intent; the lockfile freezes the fact. apm.lock.yaml records resolved source identities and deployment ownership. Unchanged Git intent replays the locked graph; changed declarations or local sources require reconciliation.
  • Identity depends on source type. Git commits, local paths, and registry archive identities are not interchangeable. Package-tree hashes use actual bytes; deployed UTF-8 hashes normalize CRLF.
  • Frozen checks are limited. Missing locks and the tested missing Git declaration fail; a newly declared local path can install and rewrite the old lock. Compare the committed contract before/after, and audit supported content separately. Cold CI replay may need network.
  • apm lock leaves harness files alone and retains existing deployment state. A fresh resolution-only lock has no previous ownership to retain. apm find traces recorded files; neither a lookup nor an SBOM authenticates a publisher.
  • Never hand-edit the lockfile. Fix the manifest, regenerate, review the diff like a dependency change, and commit the re-locked file. New locks omit generated_at; the current exercise proves a no-op with complete lock bytes and expected native outputs.
  • Meridian's CI break was a new Git declaration missing from the committed lock, not an upstream ref moving. Priya's lasting fix is reconcile-review-commit.
