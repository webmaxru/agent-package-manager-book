Two questions at the same gate

A lockfile tells you which dependency will arrive, not whether your organization permits it. An npm lockfile is not an approved-suppliers list; agent context needs the same distinction. Chapter 8 introduced content scanning, hashes, and scoped trust decisions. Those checks help detect suspicious content or changed bytes; a clean result does not prove benign intent or authenticate a publisher. A second question has no universal answer: may our developers install some-org/some-skill? is the GitHub MCP server approved? which compilation targets do we support? That depends entirely on your organization's risk posture, contracts, and compliance regime.

That second question is Governance — APM's third promise, “governed by policy” (the three promises). Where the integrity checks are built into the tool, governance is declared: an org authors an allow/deny contract in apm-policy.yml. Applicable policy and security checks gate agent-readable deployment; acquisition, staging, and cache writes can happen earlier. Policy checks declarations against organizational rules, not the meaning or future behavior of a prompt (0.31.0 policy guide, install boundary).

Integrity and governance answer different questions about the same installation.
  Security (Chapter 8) Governance (this chapter)
Question Does this artifact pass the applicable integrity and trust checks? Is this artifact allowed here?
Source of authority Built-in checks and explicitly scoped trust decisions Declared — the org authors apm-policy.yml

The two verdicts are independent. A package can pass its scan and hash checks yet be denied because it comes from an un-vetted source; an allowed source still runs through the security scan. So beware the twin misconception — “governance is just more security,” and its inverse, “if it's allowed by policy it must be safe.” Neither holds. Policy is not an antivirus, and an allow-list is not a safety certificate.

Policy is deliberately visible to developers yet authoritative for the org. It fires on a developer's own local apm install and prints an inline violation with a remediation hint — but an authoritative org baseline must not depend on an unreviewed checkout override. As Chapter 1 foreshadowed, apm-policy.yml is an org-remote authority: the policy repository is protected by CODEOWNERS and branch protection, and discovery uses your project's git remote. Local files are useful for inheritance rehearsals and explicit audits; merely naming a checkout file apm-policy.yml does not make install discover it. The required CI job must protect its source selection and environment as well as its command. Keep the install/runtime distinction from the APM README: apm-policy.yml governs what gets installed; your agent harness governs what the live agent may do. This is not a runtime sandbox or a permission system for agent behavior. APM's separate script and executable-consent surfaces remain Chapter 8's concern.

The policy file: apm-policy.yml

The allow/deny contract is a YAML declaration. Dependency rules restrict sources and require packages or bounded direct constraints; MCP rules restrict connection declarations and transports; compilation rules restrict destinations. Manifest and unmanaged-file rules make reviewable intent and file ownership auditable. Cache settings govern availability of that contract, not package trust.

This is a trimmed excerpt of the current schema fixture, not an exhaustive policy or a recommended organization-wide default. In the PowerShell examples, $Apm means the absolute path to the prepared 0.31.0 executable, never a PATH-selected CLI. Local commands use an isolated scratch copy of the current policy/ fixture; the worked example explains the complete input and baseline.

For an allow list, null means no opinion, [] means allow nothing, and a populated list means only matches. Deny wins over allow. A require list adds mandatory packages; the worked policy includes a version-pinned requirement. A * glob stays within one path segment; ** can span segments (matching rules).

Matching uses canonical GitHub/registry owner-repository casing, not a blanket lowercase conversion of every identifier. In the registry control, OPERATIONS/** matched operations/parent: the allow policy audited 0, the deny policy 1. GitHub normalization is source-grounded at this target; refs, subpaths, local paths, and MCP identities are not all case-insensitive. Preserve their actual spelling (source-aware policy matching).

Inspect what loaded, not just what you wrote

apm policy status reports the source, resolution outcome, warnings, cache state, and effective rule counts. Its --policy-source accepts a local path for rehearsal, or an organization/repository/HTTPS source. --check tests policy resolution, not whether the project complies. Both the warn and block files in this chapter resolve successfully; only their audits distinguish compliance outcomes.

The correct policy key is compilation.target.allow. A top-level targets in a policy is unknown: 0.31.0 warns and registers no target rule. That is different from the valid targets list in the consumer's apm.yml.

One contract, two enforcement points

The reviewed authority is evaluated during install and CI audit. They share policy semantics, but do not exercise identical checks (policy enforcement points):

  • Install-time preflight. apm install discovers policy from the git remote and evaluates applicable install rules before agent-readable deployment. Do not turn this into a promise that acquisition and staging write nothing, or that a failed multi-package command rolls back every earlier success. There is no --policy override on apm install; the attempted override returned exit 2 in policy-install-no-override-flag. A local policy rehearsal is not a live organization-discovery test.
  • CI audit. apm audit --ci --policy adds policy checks to the lockfile, ownership, integrity, and replay checks from Chapter 7. This includes audit-only concerns such as required manifest fields, scripts, and unmanaged files. Use it as a required merge check with protected inputs. Passing --policy to bare audit without --ci only produced an ignored-option warning in policy-source-without-ci; it did not enforce the policy.

Audit can produce the JSON report used below or a selected SARIF report for Code Scanning; SARIF is not an automatic upload. A cold replay can fetch lock-pinned content into scratch, so audit is not universally offline and there is no universal fixed check count. This chapter's local-policy fixture needs no external package fetch (audit modes and formats).

The enforcement dial: warn and block

The top-level enforcement field has three modes — off, warn, block. It gives you a measurement phase before a rule becomes a merge gate. There is no general per-rule enforcement switch. For the ordinary required-packages violation in the worked example, with the baseline clean:

Tighten-only inheritance: enterprise → org → repo

A shared baseline needs room for stricter product teams, not a way for each repo to undo it. Policies compose through extends, canonically an enterprise hub → org policy → repo child. The merge is tighten-only: a child's relaxation attempt leaves the parent's restriction effective. It need not make parsing fail (0.31.0 inheritance implementation).

Tighten-only composition: target source plus local and HTTPS inheritance observations at APM 0.31.0.

The target's companion schema page has a conflicting inheritance table: its suggestion that child [] can clear inherited deny/require lists, or that a child freely overrides fetch_failure, does not describe the observed implementation. Exceptions therefore flow upward to the owners of the governing parent. Adding an allow entry does not cancel a deny; review and narrow the restriction itself. A child file is not a waiver.

Roll out by measurement, not by switch

A new policy rule is retroactive: the next apm install or CI audit in every consuming repo runs it against dependencies that were legal yesterday. Flip straight to enforcement: block and every repo that already has a violation fails on its next run — you spend the day rolling back instead of rolling out (Policy pilot). So warn is not a lesser mode you skip — it is the measurement phase that makes block safe. The recommended sequence is four steps:

  1. Author in warn, rehearse locally, then review it into the protected org policy repository. Meridian keeps meridian-finance/.github/apm-policy.yml; the new preferred GitHub location does not require relocating the story.
  2. Measure the warnings and structured audit findings, using JSON or a deliberately configured SARIF/Code Scanning integration. A green warn-mode check is not a zero-violation count.
  3. Remediate by reviewing, pinning, upgrading, or replacing offending direct dependencies, or satisfying required-package rules. Exceptions require review at the governing parent, not an empty child deny/require list.
  4. Block after the pilot's findings are resolved or its parent rules deliberately amended. Stage a small rule set or pilot a stricter child in a narrower scope: block applies to that entire effective policy, not just one inherited rule.

For engineering leaders

Turning on governance is change management, not a config toggle. The instinct to flip enforcement: block on day one is the fastest way to break every repo at once and burn the org's trust in the whole program. Sequence it instead: ship in warn, measure the fleet-wide violations through Code Scanning for a sprint or two, have teams fix the top offenders, then block a small, remediated rule set or a stricter child scope; all rules in that effective child policy share its enforcement mode. Governance that earns trust by making a problem visible before it becomes blocking will stick; governance that fails everyone's build on a Tuesday will be disabled by Wednesday. Decide three things explicitly: who owns the org policy repo (protected by CODEOWNERS/branch protection), which rules are high-risk enough to block first, and how exceptions are granted — upward, at the parent, in a file that doubles as your audit log. Protect the required CI job's environment and selected policy too: a green baseline with policy disabled is not governance. Record the pinned APM 0.31.0 version; the engine remains early preview.

Recap

  • Security vs. governance are two questions at one gate. Security checks integrity and scoped trust; Governance asks “is it allowed here?” Neither an allow list nor a clean scan proves benign intent. Policy gates installation, not the live agent's capabilities.
  • Write and inspect the real schema. Target rules use compilation.target.allow. Unknown top-level keys warn; known invalid types fail parsing. allow: null = no opinion, [] = allow nothing; deny wins. Status resolution is not rule compliance.
  • Know each check's scope. Install discovers policy automatically; explicit sources belong to status and CI audit. The pin rule checks direct declarations, plural-only target audit has a coverage gap, and mcp.trust_transitive is parsed but not enforced. Keep Chapter 8's actual MCP trust boundary separate.
  • The rollout is warn → measure → remediate → block. The same missing requirement audited 0 in warn and 1 in block. Baseline and mandatory-hash failures are not made harmless by the warn dial.
  • Inheritance is tighten-only. Enterprise → org → repo: allows intersect, deny/require lists union, severity escalates. Local extends works; empty child lists cannot erase parent restrictions. Warm cache must retain them too. Exceptions require parent-owner review.
  • Protect the enforcement point. Host-specific discovery, consumer policy.fetch_failure_default: block, the actual loaded policy, and controlled CI inputs matter. Explicit policy beats the bypass flag, not the observed environment disable. A hash mismatch alone did not guarantee audit failure.
  • The engine remains early preview at APM 0.31.0. Pin the executable and retain both successful and deliberately failing controls; historical 0.23.1 examples are not fresh verification.
