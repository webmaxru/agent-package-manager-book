After this chapter you can run APM's four-command consumer loop — apm init, apm install <pkg>, bare apm install, and apm run <script> — and tell its two install jobs apart: add (grow the manifest and re-lock) versus restore (replay unchanged intent from its lockfile). You will read the lockfile entry an install writes, know why a no-target install stops with exit 2 instead of guessing a harness, and know why a script that names a harness needs that runtime CLI on your PATH. This is the operation that turns Chapter 4's declaration into the same supported context in each tool's native format — the moment Portability stops being a promise and becomes a fact.

A manifest is a recipe, not a meal

Chapter 4 gave Meridian an apm.yml. On its own, that file changes nothing about what an agent sees: no instruction is in force, no prompt is available, no MCP server is wired up. A manifest is a declaration of what should exist; something still has to make it exist. Install is that something. It resolves declared dependencies, materializes their content, and integrates eligible primitives and local sources for the selected, supported targets. The resulting lockfile records installed state for the next contributor (APM 0.31.0 install reference).

We call this move materialization: turning the declared state (apm.yml plus its lockfile) into real files each tool reads natively. It is where the book's first property becomes observable. Chapters 1–4 argued that scattered, hand-copied context drifts; a manifest only ends that drift if there is a single, mechanical way to realize its intent. Portability is not cross-harness byte equality: Copilot instructions, Claude rules, and Cursor rules can have different frontmatter while expressing the same source instruction. Reproducibility compares each target's output with the corresponding output from the same sources, lockfile, targets, and CLI version. Editing the manifest without installing leaves the declared and materialized states out of sync — the very gap Chapter 6 formalizes.

Install is not “just downloading packages,” either. Think resolve, policy gate, scan, integrate, lockfile: applicable policy and security checks gate agent-readable deployment. Acquisition, cache, and staging writes can happen earlier; the scan covers the authorized deployable content, not every file in a source repository. That boundary is Chapter 8's subject; here it is enough to see install as gated deployment, not a copy (install behavior and safety). The package and native-rule installs in this chapter record apm.lock.yaml, seeding Reproducibility. An empty or compile-only operation need not produce a lockfile; successful exit alone does not prove materialization.

Restore vs. add: one command, two jobs

The single command apm install does two conceptually different things depending on whether you hand it an argument. “With no arguments it installs everything from apm.yml. With one or more PACKAGE_REF arguments it adds those packages to apm.yml … and installs only what was added” (apm install). With an unchanged manifest and matching lockfile, bare install is a restore: it reuses the locked dependency graph. apm install <pkg> is an add — it declares a dependency in dependencies.apm, installs it, and re-locks.

These are the two halves of team dependency work. Add is how the manifest grows — a reviewable change to project state, exactly like npm install <pkg> editing package.json. Restore is how everyone else catches up without thinking, and it is where the whole book's onboarding promise lands: git clone + apm install replaces the wiki page, the Slack thread, and the “copy my prompt files” dance from Chapter 1. Crucially, unchanged intent replays; changed intent is reconciled. Editing a dependency's ref, changing local sources, or installing without a lockfile can cause ordinary install to resolve or materialize something new. For a deliberate refresh of an unchanged declaration, use the consent-gated apm update workflow in Chapter 7. Do not confuse replay with refresh — but do not expect an old lock to overrule a ref you explicitly changed, either (locked replay and fresh resolution).

One install command, two jobs

You already met apm init in Chapter 4: it “creates a minimal apm.yml … so you can start running apm install immediately” (apm init). Plain apm init --yes in an empty directory still creates only apm.yml — no source tree, deployment, or lockfile. Existing context has a separate onboarding path below. Then the other three verbs do their usual jobs: add and restore materialize the manifest, targeting decides where files land, and apm run executes a declared script.

Restore: bare apm install replays unchanged intent

Re-running apm install with no argument is the onboarding path from the Meridian beat. With unchanged declarations and a matching lockfile, Git dependencies reuse the locked graph, including transitive manifests. Local source files must also remain unchanged to reproduce their outputs. An intact apm_modules/ tree or cache can serve a replay; a fresh clone may need network access to hydrate the same locked source. Cache availability affects acquisition, not which commit the lock selected.

In 0.31.0, newly generated locks omit generated_at; legacy locks may retain it. Compare complete lock bytes and the expected native outputs, not a clock. The current local and public fixtures produced byte-stable locks on replay. Some restores now print No changes -- install state already up to date; others still print an installed dependency count. Neither wording is a universal completeness check (lockfile and replay contract).

For CI, apm install --frozen requires an existing lock and performs limited structural checks. It can still fetch locked content into a cold cache. In 0.31.0, its direct-dependency presence check skips local paths: a newly declared local dependency can still deploy and rewrite the old lock with exit 0 (frozen consistency check). It is not an on-disk content audit; that separate job belongs to apm audit. We use both in the current exercise, then develop them in Chapter 6 and Chapter 7.

Targeting at install time — no implicit “one true harness”

Install deploys into targets — the target-vs-harness split from Chapter 3, now doing visible work. Which harnesses receive files is resolved by an explicit precedence chain, not a hardcoded favorite: --target > apm.yml targets: > a configured default > auto-detection of harness directories already present (apm install). In the add above, the --target flag won (source: --target flag); on the next bare install, the manifest won (source: apm.yml). With an existing manifest, the flag is a per-invocation override; it does not replace the authored target list. Bootstrap is different: a positional add with no manifest can create apm.yml and persist the supplied targets. Pin and review targets: for a durable choice rather than relying on a flag from someone's earlier command (selection and bootstrap).

Targets authorize destinations; package restrictions can narrow that set, not expand it. When a manifest's target set changes, install reconciles recorded ownership rather than treating whole harness directories as disposable. The tested input was an eligible APM package with a co-located legacy plugin.json marker. In the marker-free control, reducing four manifest targets to Copilot removed stale managed outputs for the other targets while retaining Copilot's outputs and the package source. Source files, surviving shared owners, and unrelated human-authored context are not blanket cleanup targets (deployment ownership).

This control omitted only pkg/plugin.json before first install; install and CI audit exited 0 before and after contraction. With the legacy marker present, cleanup still worked, but a 0.31.0 replay defect made CI audit expect legacy commands, exit 1, and modify apm_modules/ (not authored sources, the lock, or deployed files).

Meridian's three targets consume native per-file rules. Do not generalize that to every profile: some instruction targets, such as Codex, need explicit apm compile for aggregate AGENTS.md context. The local-instruction-only Codex probe exited 0 without a lockfile or AGENTS.md; compilation was a separate step. Default compilation also preserved an existing unmarked, hand-authored root file (target matrix). This is Portability with explicit boundaries, not an implicit “one true harness.”

Run a declared script: apm run (experimental) and apm preview

The fourth verb executes a script from the manifest's scripts: block. It is stamped experimental — “the run command surface is marked experimental … flags and behavior may change before 1.0” (apm run). It is also more than literal shell: for a script like copilot -p .apm/prompts/checkout-review.prompt.md, apm run compiles the .prompt.md (frontmatter stripped) and injects the resulting content into copilot -p <content> — the prompt file is compiled, not passed verbatim. Then it shells out to the named runtime. Critically, APM does not ship the runtimes: “the runtime CLI must be on your PATH” (Run scripts). That requirement follows the script: an ordinary shell script does not require an AI runtime.

apm preview is the compile-only sibling: it writes the script's compiled prompt to .apm/compiled/ without invoking the runtime. For a local prompt this is offline and incurs no inference cost, ideal when you only need to inspect compilation. The current small probe declares review: "copilot -p .apm/prompts/review.prompt.md"; its shorter filename is separate from Meridian's checkout-review.prompt.md.

A successful preview proves compilation, not a successful agent session. The historical worked example below records a real Copilot invocation; it was not repeated for this update. Current execution checks used only a harmless shell command and a deliberately missing executable.

For engineering leaders

Onboarding becomes measurable. The Chapter 1 ritual — a wiki page, a Slack thread, and copying prompt files from a colleague — had no clear “done” and drifted the moment someone edited a local file. Restore replaces it with a two-step, verifiable outcome: git clone then apm install, after which you can check the expected target-native context against reviewed sources. Make restore part of your repo bootstrap — the make setup target, the dev-container postCreate, the first line of the contributor guide — so Portability is the default a new hire gets for free, not a checklist they might skip. “Did onboarding work?” stops being a feeling and becomes “did install succeed, did the expected files and configurations arrive for the declared targets, and were any skips understood?” Exit 0 is necessary for a successful install, not proof that every requested capability arrived; the integrity checks in Chapter 7 add another measurable gate.

Restore or add? Pick by intent

Both jobs use the same command; the argument distinguishes add from the normal install path. Choose by intent: unchanged manifest and lock mean replay, while edited declarations require reconciliation.

Which form of apm install to reach for, by intent.
You want to… Run… Because
set up a freshly cloned repo apm install (bare) with the committed lock and sources, restore replays the pinned set
add a new dependency to the project apm install <pkg>#<ref> add writes it into apm.yml and re-locks — a reviewable diff
re-materialize after editing apm.yml by hand apm install (bare) it reconciles the changed declaration; the resolved state and lock may change

Pitfall: a harness script needs its CLI on your PATH

APM is the launcher; the runtime does the work. If the CLI a script names is not installed, apm still compiles the prompt, then the shell step fails. The current scripts-probe fixture declares broken: "apm-book-nonexistent-runtime -p .apm/prompts/review.prompt.md" to exercise that boundary without invoking an agent:

That failure is a missing executable, not a failure to restore context. In a clean CI box without Copilot, apm run review cannot execute its harness. Use apm preview for prompt-compilation checks (offline, no inference cost), not a paid agent run. Reserve harness scripts for machines where the named runtime (copilot, claude, …) is present. Ordinary shell scripts remain possible without one; the fixture's echo script ran successfully. The agent runtime, not apm, incurs inference latency and credits.

Commit the clean authored apm.yml

An add is a reviewable intent change, not a reason to expect a destructive YAML rewrite. In the current local APM-dependency add, the writer preserved the leading comment, blank line, and authored target-list style. This is not a guarantee about every writer — the separate direct MCP-add probe still reserialized its manifest (APM dependency-edit behavior). Review the actual diff; an unchanged bare replay leaves the authored manifest alone.

Commit apm.yml, the generated apm.lock.yaml, authored local sources, and the reviewed deployed harness files. apm_modules/ is auto-gitignored and materialized again when needed, not necessarily rebuilt on every replay (Install packages). A local path: is not a Git version pin: its source must travel with the repository and remain available. Keep durable target choices in targets:, whether authored directly or intentionally persisted during bootstrap.

Package replacement is staged so a failed replacement can retain the last-good active package; that is not an all-or-nothing promise for an entire multi-package batch. Ownership-aware reconciliation is also not permission to delete human-owned source directories (replacement and install-state boundaries).

Recap

  • Install materializes the manifest. apm.yml is a recipe; install is the meal — it resolves, gates, scans, and deploys supported content. The package and native-rule examples record apm.lock.yaml; an empty or compile-only operation may not. This is where Portability becomes a fact, and it seeds Reproducibility as a by-product.
  • The daily loop is four commands, one habit: apm init to scaffold once, apm install <pkg> to add, bare apm install to restore, apm run <script> to run. Everything heavier is lifecycle (Chapter 7). Discovery with consented apply is a separate migration aid: it declares existing packages without installing them.
  • One command, two jobs. Bare install replays unchanged intent from the locked graph; apm install <pkg> adds a declaration and re-locks. Ordinary install reconciles edited intent, and cold restores may need network. Compare lock bytes and native outputs — new locks have no generated_at timestamp to compare.
  • Targets resolve by an explicit chain (--target > apm.yml targets: > configured default > auto-detect). The flag overrides an existing manifest for one run; bootstrap can persist it. Work needing a destination but lacking a target exits 2, while mixed successful installs can include skips. Check what arrived.
  • apm run is experimental and executes the command the script names; a harness script needs its CLI on PATH. apm preview compiles local prompts without runtime cost, but proves neither agent execution nor installation completeness.
  • Meridian reached v0.2.0 (one pinned dependency + one script), and Anika onboarded with git clone + apm install — the Chapter 1 drift, solved.
