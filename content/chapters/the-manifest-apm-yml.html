A manifest is “what this project needs,” written down

Before a manifest, a project's agent context is whatever files happen to sit on each machine — the exact drift Chapter 1 diagnosed at Meridian: a copilot-instructions.md here, a private review.prompt.md there, Cursor rules no one else can see. Nothing declares what the project needs; each laptop is its own source of truth, so the setups quietly diverge. A manifest replaces “whatever is on my disk” with “what this repository declares” — one version-controlled file that travels with the code. This is where portability stops being a slogan and becomes a file you can open in a pull request.

In APM that file is apm.yml, and the docs describe it as a contract: it “declares the full closure of agent primitive dependencies, MCP servers, scripts, compilation settings … for a project” and is “the contract between package authors, runtimes, and integrators” (manifest schema). Only two fields are required to parse — name and version — and everything else is optional (manifest schema §2). The examples here use APM's current working-draft shape, without an explicit schema selector; the init template is a starting point, not the complete set of allowed fields (APM 0.31.0 manifest reference).

Chapter 1 ended with a sketch of Meridian's apm.yml and called it “a promise, not yet a program.” This chapter makes it real: the same shape, now a file the tool actually reads. If you have ever opened a package.json, you already know how to read it — “the shape mirrors package.json on purpose: name, version, dependencies… scripts” (package anatomy).

What the manifest is, and what it is not

Two distinctions keep the rest of the book straight. First, a manifest is not the per-machine files it replaces. Those were many hand-edited outputs; the manifest is one authored input, committed to the repo, that those outputs are generated from. You edit the declaration and source — not the APM-managed copies under .github/, .claude/, or .cursor/. Those directories can also contain human-owned files; their location alone does not make every file generated output.

Second, a manifest is not a lockfile. The manifest is human-authored declared intent — what you want, which may include a moving branch or a version range. The lockfile (apm.lock.yaml, Chapter 6) is the machine-generated resolved state — the exact commits and content hashes you actually got. The manifest says what; the lockfile records exactly which (package anatomy). This chapter is entirely about the first file.

The manifest is the Portability surface — its whole job — but it also seeds the other three properties without yet delivering them: it is the input the lockfile resolves (Reproducibility, Chapter 6), the surface a policy inspects (Governance, Chapter 9), and the declaration that makes provenance reviewable (Provenance / security, Chapter 8). Get the declaration right here and the other three chapters have something honest to work with.

A declaration also sets an authority boundary: eligible package manifests and component declarations determine what can be deployed; directory conventions supply defaults where the relevant declaration is absent. Selected targets define the destination set, and package or per-dependency restrictions can narrow it, not silently add harnesses. That is reviewable deployment intent, not a guarantee that an agent obeys a rule or runs in a sandbox (package authority; Chapter 8's runtime boundary).

Misconception: “apm.yml is just config for the CLI”

It is not tool-local configuration. apm.yml is the project's shared, harness-agnostic contract, and any conforming resolver — not only the apm CLI — can consume it “to install, compile, run, and pack agentic workflows” (manifest schema, abstract). It belongs to the repository, committed next to your code, not to a workstation.

Two of those keys read straight out of Chapter 3. targets is the target ≠ harness distinction, now written down: you declare the targets, and the harness still runs independently. Pinning them in the manifest makes the destination choice repeatable for developers and CI, rather than silently tracking whichever tool folders happen to exist on the last person's machine (manifest schema §3.6). Meridian authors in .apm/; installed copies go in apm_modules/

A manifest brings your own sources and referenced packages into the same deployment workflow. Meridian's locally-authored primitives live under the .apm/ source tree (instructions/, prompts/, skills/, agents/, hooks/) — “the conventional source root for APM packages.” Referenced packages are declared under dependencies.apm and materialized at install time into the generated, gitignored apm_modules/. They can come from Git, local paths, or an enabled registry. You edit your source; you never hand-edit apm_modules/ (package anatomy).

.apm/ is Meridian's chosen convention, not the only supported layout. Skills and plugins can retain their native source trees. An eligible apm.yml — accompanied by .apm/ or APM/MCP dependencies — takes precedence over a co-located plugin marker; metadata-only apm.yml does not force that route. Root skills and skill collections are separate supported forms (package layouts and precedence).

A root SKILL.md beside apm.yml is a supported hybrid layout. Do not confuse that with setting type: hybrid: the top-level type field remains reserved for future overrides, not an active switch for selecting primitive types (reserved type field).

For Meridian's layout, includes: auto explicitly consents to local content. With no remote dependencies, apm install treats this repo as the source package and projects its eligible .apm/ primitives to the selected targets (your first package). That is precisely Meridian's first manifest: one valid local instruction, zero remote dependencies. Consuming other people's packages (Chapter 5) is an addition to local authoring, never a precondition for it.

The two dependency buckets — shape now, installs in Chapter 5

Meridian declares no dependencies at v0.1.0, but you should recognize the two buckets used here: dependencies.apm references packages, while dependencies.mcp declares tool connections. Both accept lists of strings or typed objects. The following are separate fixture examples, not additions to Meridian's first manifest.

The source identity implements Chapter 2's pinning lesson. In a Git object, use ref, not registry-style version; unknown object keys are rejected. path selects content inside that repository. Git objects also accept explicit clone URLs for other Git servers. A tag such as #v1.0.0 is readable but can be moved; the full commit above fixes the source revision, and the lockfile records the resolved graph (Git dependency forms).

Without git, a path: ./pkg object refers to a local package. alias gives it a local resolution name; skills selects from the skills it actually declares, and dependency targets intersects the install's target set. This is the authority boundary in concrete form:

That fixture's legacy plugin.json declares "skills": ["./skills/kept", "./extra/custom"]; an extra conventional skill directory is not permission to deploy it. An explicit "skills": [] means none, while omitting the key permits conventional discovery. Consumer selection cannot resurrect undeclared skills (declaration-first plugin intake).

Git remains the default path, not the only shipped source. APM 0.31.0 includes experimental REST registries, enabled explicitly with apm experimental enable registries. A named registry supplies the endpoint; its dependency object uses id and version, not Git's ref. The client and HTTP API exist; that does not establish a Microsoft-operated public searchable hub (registry guide).

A configured default registry can reroute plain owner/repo#selector shorthand. Explicit git: stays Git, so it makes the source choice unambiguous even on a machine with a registry default. Keep package registries distinct from MCP registries and Git proxies; distribution choices return in Chapter 10.

MCP entries describe connections, not ordinary primitive packages. The self-defined object below supplies a name, transport, executable, and arguments. The list also accepts MCP registry-reference strings; objects are not its only legal form (MCP dependency forms).

Reviewability includes the edit itself. The current APM dependency writer preserved the tested leading comment, blank line, and target-list style when adding a package. A direct MCP add uses a separate path that still reserialized the tested manifest and removed its comment. Review the diff after either operation; do not assume every writer preserves formatting (APM dependency writer; Chapter 5's add workflow).

For engineering leaders

This is the moment agent context enters code review. Because the manifest is a small, version-controlled text file, every change to it is a diff — and a diff is something a teammate can review in a pull request. “Added microsoft/apm-sample-package#v1.0.0,” “targeted cursor,” “moved a source from a branch to a tag” are now visible, reviewable edits rather than invisible per-machine changes. A pinned ref shows whether a dependency is immutable or moving; the source shows whose code it is. The accountability gap from Chapter 1 — security could not say which tools were installed or whether a prompt came from an approved source — closes the day these answers live in a committed file. The question to put to your team: should adding or changing apm.yml require review the same way changing package.json does? The policy layer that enforces the answer is Chapter 9; the reviewable diff is what makes that enforcement possible.

Keep your first manifest minimal

The dividing line from Chapter 1 still holds: commit an apm.yml the moment context is shared and plural — multiple developers, multiple harnesses, onboarding that should be reproducible. For a spike you will throw away, a manifest is ceremony you do not need yet.

When you do write one, resist the urge to fill every key. A strong first manifest declares only three things: identity (name, version, a real description), targets (the harnesses your team actually uses), and the local primitives it authors under .apm/ (via includes: auto). Remote dependencies and scripts are real features — they are just Chapter 5's beat, added when you need them, not scaffolding to fill in up front. The empty dependencies buckets and scripts: {} that apm init leaves behind are valid empty declarations; there is no need to fill them yet.

Pitfall: the init template is not the whole schema

author is attribution; license: MIT is valid optional license metadata. Plain init's omission of license is not a prohibition. Likewise, devDependencies separates author tooling from the dependency closure you publish. Put maintainer-only primitives outside the selected source layout and reference them there, rather than expecting an install-time includes list to hide them (optional metadata and dev dependencies).

Pitfall: includes has an operation-specific boundary

includes: auto explicitly consents to local content in the selected layout. Omitting the field retains legacy implicit consent and can produce an includes-consent audit advisory. At install, even an explicit path list records consent rather than filtering discovery: the 0.31.0 control listed one instruction, but both that instruction and an unlisted second instruction deployed.

At plugin pack, the list is exhaustive. With includes: [skills/unlisted], the pack control shipped only that named root skill, not the unlisted .apm/ content; a missing listed path stopped packing before writes. With auto, .apm/ presence selects the APM-native layout rather than silently combining it with root plugin sources. Keep auto for Meridian's first manifest, but do not call includes either “always an allowlist” or “never an allowlist” (includes semantics; packing in Chapter 10).

0.31.0 limitation: the control containing both .apm/ and root skills packed the selected content, but apm audit --ci exited 1: replay expected the root unlisted skill and treated the installed secure-payment-review skill as orphaned, across the shared and Claude paths. That source-selection disagreement does not occur in the clean, single-layout instruction example below. Keep the pack result distinct from an install-and-audit guarantee.

Target selection is a declaration, not a memory of the last command

Prefer a nonempty plural list: targets: [copilot, claude, cursor]. Legacy target is still accepted, but declaring both keys is a parse error. targets: [] is invalid. Legacy manifest all warns and makes the whole field act as omitted, including sibling targets; it does not select every harness.

Selection follows --target → manifest targets → saved default → filesystem detection. With an existing manifest, the flag overrides only that invocation; it does not replace the authored list. An install that bootstraps a missing manifest can persist its supplied targets. Commented targets leave the choice to those other inputs; pin the list for a shared repo (target selection and bootstrap).

A local path is not an immutable Git pin: its source must remain available with the project. Nor does apm install --frozen universally veto declaration changes. In 0.31.0, a newly declared local-path dependency can deploy and rewrite an existing lock; see Chapter 5's verified exception. Frozen's limited structural checks are not a runtime security guarantee or a content audit.

Recap

  • A manifest turns “what this project needs” into reviewable, version-controlled state. In APM that file is apm.yml — the Portability surface, and the input that seeds reproducibility, governance, and provenance in later chapters.
  • You author one input; APM generates the outputs. The manifest is declared intent (what); the lockfile is resolved state (exactly which, Chapter 6).
  • Plain empty-directory apm init writes one file with sensible defaults: identity (name/version/description/author), commented targets, two empty dependencies buckets, includes: auto, and scripts: {}. Only name and version are required to parse.
  • includes: auto consents to the selected local source layout. An explicit list does not filter install discovery, but is exhaustive for plugin packing. You edit source; APM owns its materialized copies, not every file in a harness directory.
  • The scaffold is not the whole schema: license is valid optional metadata and devDependencies keeps author tooling out of the published dependency closure. A hybrid layout does not activate the reserved type: hybrid field.
  • Pin targets for a durable destination choice. Use ref on Git objects, id/version for registry packages, and path for local references. MCP accepts registry strings as well as server objects. Review the declaration, rather than relying on directory names or the last invocation's flags.
  • Meridian committed its first real manifest (v0.1.0): identity, three targets, and one local instruction that apm install deployed to Copilot, Claude Code, and Cursor — one source, three native files, zero per-harness edits.
